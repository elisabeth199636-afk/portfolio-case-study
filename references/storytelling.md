# 案例叙事与证据

## 从素材提炼价值

先建立事实清单，再选择主线。每个关键判断使用以下证据链：

| 环节 | 需要回答 | 可接受的依据 |
| --- | --- | --- |
| 问题 | 谁在什么情境遇到什么阻碍？ | 用户背景、旧版可见问题、有来源的研究 |
| 判断 | 为什么选这个方向？有哪些约束或取舍？ | 过程稿、对比方案、设计说明、决策记录 |
| 设计证据 | 哪个变化承载了判断？ | 新旧同任务对比、流程、状态、形象推导、视觉规则 |
| 价值边界 | 现有材料最多能证明什么？ | 设计交付、实际应用证据、有明确口径的验证或结果 |

内部建立“结论—依据—证据状态”的对应关系，交付时在章节素材和真实性检查中体现。不要先写故事，再倒推不存在的证据。

区分两个维度：

- **项目状态**：实际完成、概念提案、后续规划、未知。按交付物分别标注，不必强行给整个项目同一状态。
- **信息依据**：已提供事实（注明来源）、可见观察、设计推断、待补充。用户叙述与原始证明可以有不同证据强度。

“已完成设计”“已上线”“已验证效果”是三件事。每条结果都应有来源，缺口保持可见。

## 定位与卖点

一句定位建议包含：服务对象或情境 + 核心问题 + 主要设计动作 + 当前交付边界。缺失部分直接标记，不猜行业、用户群或业务目标。

主要卖点应对目标岗位有意义、有足够设计证据、能体现用户本人作出的判断。没有目标岗位时，以用户提供的职责与证据选择临时主线，注明定位待确认。

- 只有最终截图：可以谈呈现、层级和规则的可见特征，过程和效果待补。
- 有过程稿：提炼真正改变方案的取舍，不按时间罗列所有稿件。
- 有验证：核实对象、时间、样本、方法、口径与局限，再决定结论强度。
- 只有口述：注明“来自项目说明”，不写成“从截图可见”。

## 七种叙事功能

| 功能 | 读者问题 | 展示内容与边界 |
| --- | --- | --- |
| Hero 最终成果首屏 | 这是怎样的成果？ | 代表性成果主视觉、观点标题、简要定位；概念或未上线状态可见。缺成果素材时待补，不虚构画面描述 |
| Overview 项目概览 | 范围是什么，你负责什么？ | 背景、目标、约束、职责和协作边界。时间、团队规模、主导程度未知则不填 |
| Problem 现状问题 | 为什么值得做？ | 旧版证据或有来源的需求，具体到任务、识别、规则或场景；无旧版不杜撰痛点 |
| Strategy 设计策略 | 为什么这样设计？ | 目标、原则、真实探索、约束与取舍。后补分析与原过程分开 |
| Solution 核心设计 | 如何解决问题？ | 按关键决策组织，可拆多个章；每章一条判断及证据，不逐屏介绍功能 |
| Application 应用 | 怎样在情境中工作？ | 实际应用优先；原型、样机、概念延展分别标注，不写成已落地 |
| Impact 结果与复盘 | 证明了什么，还缺什么？ | 有依据的结果、限制与复盘。无数据就展示交付范围与建议验证，不用“显著提升”填空 |

顺序以阅读理解为准：可把概览缩为首屏信息带，将 Problem 和 Strategy 合并，或把关键对比提前。解释调整服务于哪个核心问题。章节数量随证据变化，不机械生成七页。

## 标题与正文

标题给出可被本章素材支持的观点，避免“项目背景”“设计赋能”等泛词独立充当核心标题。导航可用中性短名，章节标题承载观点。

以下仅为措辞示例，不是项目事实：

- 有流程证据可写“将任务进度集中呈现”；无验证不写“任务完成率提升”。
- 有形象结构证据可写“以统一轮廓组织角色变化”；不凭设计稿写“用户认知全面升级”。
- 有规则及全量图可写“用共同骨架区分徽章等级”；缺素材时写“拟以共同骨架建立等级规则（建议）”。

正文通常一至三句：说明判断、设计动作及必要边界。细节由图注、标注与局部放大承载。每章出现两个独立问题时先判断主次，再决定拆章或删减，不为每条说明创建小模块。

## 缺失与冲突

- 缺核心问题：定位暂定，集中询问真正要解决的问题，仍可整理素材及推荐可选主线。
- 缺过程：策划需要补的决策证据，不编写“经过多轮访谈／探索”。新增对比标为回顾分析或建议补做。
- 口述与截图冲突：记录来源和位置，暂缓依赖该冲突的结论，继续其他章节。
- 无结果：写清已交付、未验证目标及验证方案；验证规划不能冒充 Impact 中的实际结果。
